# Andrej Karpathy 编码技能

将一组偏保守、强调工程纪律的行为约束整理成可复用 skill，供代码实现、修改和评审时按需加载。

## 适用场景

- 修复缺陷，但希望先明确问题边界和验收标准
- 做小范围实现或重构，要求避免过度设计
- 编辑现有代码，要求最小化改动面
- 做代码评审，重点关注假设、复杂度和可验证性
- 任务存在多种解释，需要先澄清再动手

## 核心原则

### 1. 编码前先思考

不要默认假设正确，也不要掩盖不确定性。

- 明确写出前提假设
- 如果需求有多种解释，先摆出分歧，不要静默选一种
- 如果存在更简单的方案，要明确指出
- 一旦信息不足以支撑实现，应先说明卡点再继续

### 2. 简单优先

只写完成任务所需的最小代码，不预埋未来需求。

- 不额外增加未被要求的功能
- 不为一次性逻辑引入抽象层
- 不为了“可扩展”提前设计复杂配置
- 不为不可能发生的场景堆叠防御式逻辑
- 如果实现明显偏大，应主动收敛

### 3. 外科手术式修改

编辑已有代码时，只改与目标直接相关的部分。

- 不顺手清理无关代码、注释或格式
- 不重构未损坏的邻近模块
- 保持与现有代码风格一致
- 只清理因本次改动引入的无用代码
- 发现无关问题时可以提示，但不要擅自处理

### 4. 以验证为目标推进

把任务改写成可验证的目标，并循环到验证通过。

- “增加校验”应落实为可复现的失败场景和通过结果
- “修复 bug”应先能稳定复现，再验证修复
- “重构”应在前后都验证行为不变

建议把复杂任务拆成简短步骤，并给每一步附上验证方式。

示例：

```text
1. 复现问题 -> 验证：失败场景可稳定触发
2. 最小化修复 -> 验证：目标场景恢复正常
3. 回归检查 -> 验证：相关测试或手工路径通过
```

## 使用方式

1. 先确认当前任务是否属于“实现、修复、重构、评审”这类需要工程约束的场景。
2. 开始处理前，先输出关键假设、边界和更简单替代方案。
3. 实施时遵循最小改动原则，只修改与目标直接相关的代码。
4. 完成后明确给出验证结果；如果未验证，说明缺口。

## 评估标准

以下现象说明该技能生效正常：

- diff 更小，更聚焦
- 不必要的抽象和顺手重构减少
- 澄清问题发生在编码前，而不是返工后
- 每一步改动都能对应明确的验收或验证动作

## 注意事项

- 该技能偏向谨慎和稳妥，不追求最快产出
- 对极小任务可适当简化执行流程，但不要跳过关键假设
- 如果任务本身信息不足，这个技能应优先推动澄清，而不是强行实现
